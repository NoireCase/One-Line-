# Hidden Mode Spec

> 极简线索（Hidden）是 One-Line 的新增独立高难推理玩法。
> 本文档定义玩法定位、规则、MVP 范围和关卡设计原则。
> 用于指导 v0.14.0 Hidden Demo / MVP 开发。

---

## 1. Positioning

Hidden / 极简线索是 One-Line 的**独立高难推理玩法**。

三个关键定位：

1. **不是 Classic hard+。** 不是把 Classic 的 hidden 比例从 50% 提到 80%。仅仅是"隐藏更多数字"不构成新玩法。

2. **不是 Flow / Numberlink 换皮。** Hidden 只有一条连续路径，不分多条颜色线，不引入颜色系统，没有多条独立路径。

3. **是分段关键数字推理。** 玩家根据棋盘上极少的几个关键数字，按顺序分段连接，每一步都受段长（数字差值）和全盘覆盖约束，最终还原唯一正确的一笔画路线。

Hidden 的核心句：

> **线索极少，推理极深。**

---

## 2. Player-Facing Concept

### 玩家看到什么

玩家打开 Hidden 关卡后，棋盘上只显示极少的几个数字——这些数字称为**关键数字**。例如 5×5 棋盘只显示：

```text
1、6、12、18、25
```

玩家不能靠「看下一个数字走过去」的方式推进——棋盘上没有 2、3、4、5。玩家需要根据段长约束和棋盘空间，分段推理出完整路线。

### 玩家做什么

1. 从 `1` 开始。
2. 观察下一个关键数字的位置，计算差值，判断这条路径大概需要怎么走。
3. 逐段连接所有关键数字。
4. 最终覆盖全盘，形成一条连续不重复的一笔画路线。

### 推荐玩家文案

| 项目 | 内容 |
|------|------|
| 对外玩法名 | **极简线索** |
| 内部 modeId | `hidden` |
| 一句话说明 | 线索极少，推理极深。从寥寥几个关键数字还原出唯一路线。 |
| 关卡内 HUD 提示 | 关键数字分段推理 · 全局唯一解 |
| 模式入口副标题 | 根据有限的数字线索，推理整条路径 |

## 3. Core Rules

### 3.1 移动规则

| 规则 | 设置 |
|------|------|
| 移动方向 | **正交四向**（上下左右），不允许斜向 |
| 跨格 | 不允许 |
| 路径重复 | 不允许（每个格子只能经过一次） |
| 全盘覆盖 | **必须覆盖**棋盘上的每一个格子 |
| 起点 | 必须从关键数字 `1` 所在格子开始 |

MVP 阶段复用 Classic 的四向移动和路径验证逻辑。

### 3.2 关键数字与段长约束

棋盘中少量格子显示数字，其余格子均为空白。

**段长约束：** 如果两个连续关键数字为 `a` 和 `b`（a < b），则从 `a` 所在格子到 `b` 所在格子的路径必须恰好执行 **`b - a` 次移动**。

该段包含 **`b - a + 1` 个数字位**（含起点 `a` 和终点 `b`）。若从已被占用的起点 `a` 继续前进，该段新增 `b - a` 个格子。

整条 5×5 路线从 `1` 到 `25`，总共 **24 次移动**，覆盖 **25 个格子**。

后续 solver 实现应以 **移动次数 = b - a** 为核心判断。

示例：

```text
关键数字：1、6、12、18、25（5×5，共 25 格）

第 1 段：1 → 6   差值 5，执行 5 次移动（该段含 6 个数字位，新增 5 个格子）
第 2 段：6 → 12  差值 6，执行 6 次移动（该段含 7 个数字位，新增 6 个格子）
第 3 段：12 → 18 差值 6，执行 6 次移动（该段含 7 个数字位，新增 6 个格子）
第 4 段：18 → 25 差值 7，执行 7 次移动（该段含 8 个数字位，新增 7 个格子）

总移动次数：5 + 6 + 6 + 7 = 24
总格子数（数字位）：25（每个格子恰好被路径访问一次）
```

### 3.3 必须显示的数字

- **起点 `1`：** 必须显示。这是可用性底线——玩家必须知道从哪里开始。
- **终点 `N×N`：** 建议显示。知道终点位置帮助全局推理，降低纯猜测的可能。
- **中间关键数字：** 3–4 个。总共 5–6 个关键数字（含 1 和终点）。

### 3.4 必须唯一解

每个关卡在同一组关键数字下，必须只有一条路径满足所有约束（段长、全盘覆盖、不可重复）。如果存在多条路径，该关卡不能入库。

唯一解验证由专用 solver 工具完成（见 §9）。

## 4. Difference from Classic

| 维度 | Classic | Hidden |
|------|---------|--------|
| 推理方式 | **局部推进：** 看到下一个数字，走过去 | **分段推理：** 从有限关键数字推导完整分段路径 |
| 可见数字比例 | 约 50%–60% | **约 20%（5–6 个 / 25 格）** |
| 核心约束 | 下一个数字是确定的（但不一定可见） | **段长 + 空间 + 全盘覆盖三重约束** |
| 玩家的核心问题 | 「下一个数字藏在哪里？」 | **「这一段恰好 N 步的路有几条？哪条留了后续空间？」** |
| 失败模式 | 连错 → 扣血 | 路线封死 → 发现约束矛盾 → 回退重推 |
| 解题节奏 | 步进式，一步一个判断 | **段进式，一段一次规划** |
| 对周围信息的依赖 | 高（靠相邻数字判断） | **低（只能靠段长和棋盘边界）** |

一句话总结：

> Classic 是「看清楚下一步」；Hidden 是「想清楚一整段」。

---

## 5. Difference from Flow / Numberlink

### 相似点

| 相似 | 说明 |
|------|------|
| 有标记端点 | Flow 有颜色端点，Hidden 有关键数字 |
| 路径不能重叠 | 两者都有此约束 |

### 差异点

Flow / Numberlink 的核心不在数字顺序和段长约束。Hidden 必须按数字顺序连接，并由数字差值决定每段移动次数。

| 维度 | Flow / Numberlink | Hidden / 极简线索 |
|------|------------------|-------------------|
| 路径数量 | 多条独立路径，每个颜色一条 | **只有一条连续路径** |
| 连接逻辑 | 两个同色端点直接相连 | **前一段终点 = 后一段起点，首尾连续** |
| 顺序 | 无顺序要求 | **按数字顺序严格分段** |
| 段长约束 | 无 | **数字差值精确决定每段移动次数** |
| 全盘覆盖 | 不以此为核心 | **必须覆盖全盘** |
| 颜色系统 | 需要颜色区分不同线 | **只用数字，不引入颜色** |

### 不会被误解为 Flow 换皮的原因

1. 玩家画的始终是**一条线**，不是多条。
2. 数字天然表达了顺序和段长，不需要颜色编码。
3. 段长约束 + 全盘覆盖是 One-Line 独有的双重约束，Flow 没有这个。

## 6. MVP Scope

> v0.14.0 Hidden Demo / MVP 的目标是验证「分段关键数字推理」是否成立，
> 不是发布正式 Hidden 内容。

### MVP 包含

| 项目 | 规格 |
|------|------|
| 棋盘尺寸 | **5×5（25 格）** |
| 关卡数量 | **3 关**，按难度递进：引导关 → 标准关 → 挑战关 |
| 每关关键数字 | 5–6 个（含 `1` 和 `25`） |
| 起点 | 必须显示 `1` |
| 终点 | 建议显示 `25` |
| 移动方向 | 正交四向，复用 Classic 路径验证 |
| 全盘覆盖 | 必须 |
| 路径不可重复 | 是 |
| 唯一解 | 每关必须通过 solver 唯一解验证 |
| 关卡来源 | 手工设计，存在 `src/data/hiddenLevels.js` |
| 玩法入口 | 独立 GAME_MODE（`hidden`），独立入口卡片 |
| 进度存档 | 独立 key（`cg_hidden_progress`） |
| 中途存档 | 独立 key（`cg_hidden_saved_game`） |
| 生命 | 保留 Classic 生命逻辑（错误操作扣血），MVP 给予高容错（如 HP = 10） |
| 结算 | 只记录通关，暂不评星 |

### MVP 不包含

| 项目 | 说明 |
|------|------|
| 7×7 / 9×9 | 暂缓。5×5 验证通过后再讨论 |
| 自动生成关卡 | MVP 全部手工设计 |
| 候选生成 / curated / apply pipeline | 暂缓 |
| GM Console 审核面板 | 暂缓（可先在 GM 中裸调用试玩） |
| 星级评分 | MVP 只判断通关 |
| 金币奖励 | 暂缓 |
| 道具系统 | 暂缓（提示、排除、恢复、复活均不开放） |
| 复杂解锁条件 | MVP 默认开放，无需前置关卡 |
| Portal 整理 | 不作为 Hidden MVP 前置任务 |

### 为什么用 5×5

- 5×5 是验证推理机制的最低可行尺寸。
- 25 格 + 4–5 段 = 每段 4–7 步，约束刚好。
- 手工设计 5×5 关卡的搜索空间可控。
- 如果 5×5 都做不出好的推理体验，7×7 也做不出。
- **5×5 是 MVP 验证尺寸，不代表正式 Hidden 只做 5×5。**

### 5×5 难度升级标准

v0.14.0 Hidden MVP 包含 6 个关卡，按推理深度分三类：

| 类型 | 关卡 | 关键数字 | 路径特征 | 段长特征 | 核心推理要求 |
|------|------|---------|---------|---------|------------|
| Demo 入门 | #1–#3 | 5–6 个 | 可为规律扫描（蛇形/螺旋），帮助玩家理解玩法 | 段长 2–7 步 | 理解「关键数字 + 段长约束」基本概念 |
| 轻度推理 | #4 | 5 个 | **必须打破规律性**，不能是蛇形/螺旋 | 至少一段 extra ≥ 3，至少一段 ≥ 8 步 | 开始靠段长判断，不能靠形状识别 |
| 标准推理 | #5 | 5 个 | 不规则路径，起点可在中心 | 至少一段「曼哈顿 ≤ 2 但移动 ≥ 5 步」的绕路段 | 前一段走法会影响下一段空间，需要权衡 |
| 挑战 | #6 | 4–5 个 | 完全无规律可循 | 至少一段长段（≥ 8 步）+ 至少一处空间封锁 | 全局前瞻，不能局部试错 |

**设计原则：**
- 入门关可以有规律路径（帮助上手）
- 标准关必须避免蛇形/螺旋/行列扫描
- 标准关至少需要一段明显绕行（extra ≥ 3）
- 挑战关至少需要一段长段（≥ 8 步）或空间封锁
- 所有关卡的路径应该「看起来不规则」——只有段长约束才能确定正确路线

## 7. Level Design Guidelines

### 7.1 关键数字数量

| 关键数字数 | 5×5 效果 |
|-----------|---------|
| 2–3 个 | 约束太少，多解概率极高，不推荐 |
| 4 个 | 3 段，可能可行但推理空间有限 |
| **5–6 个（推荐）** | 4–5 段，每段 3–7 步，约束刚好 |
| 7–8 个 | 段太短（每段 2–3 步），变回 Classic 步进式 |

### 7.2 段长设计

- **不要全部等长。** 全部等长让所有段看起来一样，玩家失去策略层次。
- **建议长短交错。** 短段提供确定性锚定感，长段提供大范围路线选择。
- **段长不宜超过 N×2。** 在 5×5 中，一段 10 步的路径几乎可以走到棋盘任何位置，约束太弱。

### 7.3 锚点位置

- 关键数字的棋盘位置直接影响可推理性和唯一解。
- **避免相近位置。** 连续两个关键数字如果在棋盘上相邻，段长约束（如差值 4）会迫使玩家绕路，绕法不唯一。
- **建议关键数字分散在棋盘不同区域。** 例如：1 在左上、中间锚点在右上、13 在左下、25 在右下。区域分散让每段有明确的空间方向感。
- **边缘 + 内部交替。** 让部分关键数字在边缘、部分在内部，增加路径可能性并迫使玩家在不同区域之间平衡。

### 7.4 唯一解的设计原则

每关设计完成后，应验证以下性质的错误路线均被排除：

1. **移动次数不符。** 一条候选路径的移动次数 ≠ `b - a`，直接排除。
2. **空间封死。** 当前段路径消耗了过多格子，导致后续段数无法覆盖剩余格子。
3. **全盘覆盖失败。** 所有段完成后，还有格子未被覆盖或不可达。
4. **交叉/重复。** 路径出现自交或重复经过同一格。

设计者应该能向自己解释：「为什么这段不能走另一条路线？」——因为另一条路线会（封死后续段落 / 导致剩余格子无法覆盖 / 长度不符）。

### 7.5 难度递进建议

| 关卡 | 关键数字数 | 特点 |
|------|-----------|------|
| 第 1 关（引导） | 5 | 段长分布均匀，关键数字位置明显，空间约束宽松 |
| 第 2 关（标准） | 5 | 引入一段长段，需要玩家权衡「绕路」vs「留空间」 |
| 第 3 关（挑战） | 6 | 关键数字分散，多段短段 + 一段长段，需要全局前瞻 |

- 是否接入全局 score / coins 系统

## 9. Technical Integration Plan

> 本节为建议方向，不绑定具体实现。

### 9.1 新增文件

| 文件 | 用途 |
|------|------|
| `src/data/hiddenLevels.js` | 手工 Hidden 关卡数据 |
| `scripts/verify-hidden-unique.mjs` | 唯一解验证工具 |

### 9.2 复用现有模块

| 模块 | 复用方式 |
|------|---------|
| `src/game/rules/movement.js` | 四向移动和路径交叉检测 |
| `src/game/classic/createClassicLevel.js` | 参考其配置结构（CONFIG、N、hp 等） |
| `src/hooks/usePathInteraction.js` | 复用拖拽/键盘输入（如果 Hidden 不改变输入方式） |
| `src/hooks/useGameSession.js` | MVP 复用，后续如需要可派生 `useHiddenGameSession` |
| `src/components/WinPanel.jsx` | 复用基础结算面板，文本改为 Hidden 专用文案 |

### 9.3 模式注册

- 在 `src/config/gameModes.js` 新增 `PLAY_MODES.hidden` 和 `GAME_MODES.hidden`。
- 在 `GAME_MODE_LIST` 中新增 Hidden 入口（列在 Classic 和 Diagonal 之后、Portal 之前）。
- `getClassicLevelTargetByNumber` / `getClassicTotalLevels` 不适用于 Hidden——Hidden 使用独立的关卡索引逻辑。

### 9.4 唯一解验证工具

`scripts/verify-hidden-unique.mjs` 的功能：

- 输入：一个 Hidden 关卡定义（N、关键数字列表及其棋盘位置）
- 输出：是否存在唯一解、找到几条解
- 算法：DFS/BFS 遍历，对每个候选路径验证段长约束、全盘覆盖、不可重复
- 性能：5×5 搜索空间在可接受范围内

如果验证工具不可用，手工设计的关卡质量无法保证。

### 9.5 不接入项

- MVP 不接入 GM Console 候选审核面板
- MVP 不接入自动生成 / curated / apply pipeline
- MVP 不接入 score / coins 全局系统

## 10. Out of Scope

明确本轮不做、不讨论的内容：

- 7×7 / 9×9 Hidden 关卡
- 自动生成 Hidden 关卡或候选筛选 pipeline
- GM Console Hidden 候选审核面板
- Portal 玩法整理
- 道具系统（提示、排除、恢复、复活）
- 星级评分和复杂结算
- 全局 score / coins 接入
- Classic 通关解锁 Hidden 的关联逻辑
- PWA / APK / iOS 安装包
- git tag / release / push

## 11. Expansion Criteria

### 进入下一阶段（v0.15.0 Hidden 扩容）的条件

- [ ] 3 个 5×5 demo 关卡每关都通过唯一解验证
- [ ] 试玩者能自然理解「关键数字分段推理」
- [ ] 不是靠猜——每一段都有明确的排除逻辑，试玩者能解释为什么只能这么走
- [ ] 唯一解验证工具可用且结果可靠
- [ ] 试玩反馈确认 Hidden 和 Classic 有明显差异
- [ ] 3 关的难度呈现清晰递进

### 暂停或调整方向的条件

- [ ] 5×5 无法稳定设计出唯一解关卡（即使手工反复调整）
- [ ] 试玩者无法理解段长推理，主要靠试错
- [ ] 试玩反馈认为「和 Classic 差不多，只是数字少了」
- [ ] 验证工具发现多解，且无法通过调整关键数字位置修复

### 如果暂停

- 「关键数字分段推理」方向可能不适合 5×5，考虑 7×7
- 或者方向本身需要重新设计（如放弃段长约束，改用其他推理机制）
- 不意味着 Hidden 概念被放弃——只是本轮设计方向不对

## 12. Open Questions

以下问题留待后续版本讨论，不在本 spec 中给出最终答案：

1. **7×7 扩展：** 如果 5×5 demo 成立，7×7 的关键数字数量建议多少（7–9 个？）？7×7 是否需要八方向移动？
2. **提示系统：** 是否在正式版中开放「提示当前段路径方向」的轻度提示？MVP 不开放。
3. **星级评价：** Hidden 应该用什么评价维度？「回退次数」「完成时间」「错误尝试次数」？还是和 Classic 一样做 stars？
4. **隐藏终点：** 正式版高难 Hidden 是否隐藏终点 `N×N`？隐藏终点会大幅提高难度，但也可能让推理变成猜测。
5. **Classic 解锁关联：** Hidden 是否在 Classic hard 全通后解锁？独立开放还是条件解锁？
