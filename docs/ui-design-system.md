# Linebook UI 设计规范

> 本文定义 Linebook 的产品级界面规则。Star Line 是第一套完整落地案例；规则适用于后续页面和玩法，但不要求旧页面在一次改动中全部迁移。

## 1. 视觉定位与优先级

Linebook 是“夜空中的谜题册”：深色外壳提供安静的氛围，谜题工作区提供足够明亮、稳定的阅读面。背景装饰只能烘托，不能压过关卡信息、棋盘或操作反馈。

- 游戏内容始终是页面第一视觉焦点，棋盘类玩法尤其如此。
- 夜空背景以近乎纯净的深色空间为主；少量、不规律的星点可以存在，但重复方格、成片模糊光斑和装饰纹理不得成为默认语言。
- 每种玩法可有自己的强调色，但需沿用同一套中性色、文字层级、边界和状态语义。
- 不以强发光、厚阴影或高饱和颜色替代信息结构。

## 2. 页面亮度层级

深色主题必须形成清楚的阶梯，不能把所有内容压在相近暗灰区间。

| 层级 | 职责 | 不能混同的对象 |
| --- | --- | --- |
| 页面背景 | 夜空氛围与无关留白 | 工作区、可读文字 |
| 内容层 | 普通页面卡片和导航 | 棋盘底板 |
| 游戏工作区 | 让棋盘从背景中站出来 | 页面背景、工具区 |
| 棋盘格与可操作内容 | 支持扫描和推理 | 已处理标记 |
| 已处理 / 降权信息 | 保留可确认性，不抢答题焦点 | 当前可操作信息 |
| 关键结果 | 完成、奖励、真实错误和焦点 | 常规装饰 |

棋盘底板必须比页面背景和普通内容层更清楚；未处理格必须比已排除标记更容易发现。

## 3. 颜色与状态

### 颜色规则

- 使用语义令牌：背景、表面、文字、边界、奖励、成功、警告、错误、焦点，而不是在组件内随意新增近似颜色。
- 金色只用于奖励、星点和完成等关键结果，不用于大面积底色。
- 错误红只用于真实冲突或失败；普通状态、进度和区域色不得伪装成错误。
- 关键状态不得只靠颜色表达，必须同时有文字、图形、边界或位置变化。
- 相邻区域或状态应同时具备色相 / 明度差和边界差，不能只提高饱和度。

### 状态权重

1. 当前目标、关键结果、焦点信息。
2. 当前可操作信息。
3. 已完成或已处理信息。
4. 禁用与背景性说明。

已处理信息通常应降权，不能比待处理信息更抢眼。悬停、选中和教学引导必须可见，但不应覆盖真实冲突反馈。

“降权”不等于隐藏。高密度排除标记需要比空格安静，但玩家在正常观看距离下仍应无需停顿即可确认其存在。

### 锁定内容层级

- 关卡与章节的视觉权重排序：当前可玩章节与下一目标 > 已完成可重玩 > 远期锁定。
- 远期锁定章节必须降权（更薄、更暗、更紧凑），不得让连续的锁定行和锁图标成为首屏主体，形成“锁墙”。
- 锁定状态不能只靠降低透明度表达：至少同时使用锁图标、边界形态（虚线）和「未解锁」文字。
- 降权不得改变实际解锁条件、进度与关卡顺序的准确表达。

## 4. 排版与信息层级

| 层级 | 用途 | 桌面建议 |
| --- | --- | --- |
| 页面标题 | 页面或玩法入口标题 | 24px 以上，强对比 |
| 模块标题 | 章节、面板、结果标题 | 18–20px，强对比 |
| 关卡主信息 | 玩法名、关卡名 / 编号 | 14–16px，主文字 |
| 状态数字 | 进度、计数、结果 | 至少与关卡主信息等强，数字可更大 |
| 辅助标签 | 棋盘规格、规则类型 | 12px 以上，次文字 |
| 正文 / 按钮 | 可操作文字与说明 | 13px 以上 |
| 次要说明 | 非关键提示 | 12px 以上 |

11px 以下文字不得承担玩家必须读取的规则、状态或按钮含义。灰色只用于次信息，不能替代层级设计。

玩家可见最小字号按语义执行，不做全局统一放大：

- 玩家必须阅读的信息（核心操作名、当前关卡信息、进行中的关键状态、首次教学提示）：≥12px。
- 状态数字旁的单位、结果数据的标签、导航类标签：≥11px。
- 9–10px 只允许用于不承担独立含义的内容（瞬时确认提示、hover 辅助说明、开发调试标记）；开发 / 测试内容不为了统一而放大。
- 单项调整必须有语义依据，不允许通过统一放大让卡片、按钮和布局整体膨胀。

### 信息去重与表面职责

同一信息在屏幕上只保留一个主要来源；其余位置删除、缩短或降级，不通过改写措辞保留所有副本，也不把删掉的信息用 tooltip 塞回来。

- 首页：只回答「两个家族是什么、我能继续什么」。不放选择指令、家族内玩法索引或重复规则；继续入口必须显示玩法名称与关卡号等存档上下文（只读现有存档字段推导，不改存档结构）。
- 关卡选择页：玩法切换只显示玩法名与简洁进度，页面不另设「已完成 X / X」；章节头只显示章节名和主操作，不重复棋盘尺寸、章节完成数或完整规则。
- HUD：只保留进行中必须持续查看的信息（导航、关卡身份、规则类型、进度、生命 / 资源）；已固定在棋盘旁的状态（如路径进度）不在 HUD 重复。
- 棋盘旁状态：紧贴棋盘，只保留与盘面直接相关的一行进度。
- 教学区：游戏目标与规则在首次教学或明确规则区说明，HUD 不重复整句规则。
- 结果面板（Win / Lose）：只展示结果、关键数据与下一步动作，不重新完整讲规则；规则完成语义用一处徽标或一句话表达。

## 5. 间距与布局

- 首页和关卡选择页的主内容必须落在单一、边界明确的前景表面上；卡片和关卡节点是该表面的内部结构，不得直接漂浮在页面背景上。
- 页面背景只保留低对比的大尺度明暗变化，不使用高频重复方格、密集星点或可被误读为内容边界的纹理。
- 游戏页建立连续中轴：`关卡信息 → 棋盘 → 状态反馈 → 操作`。
- 棋盘与状态区保持紧邻；状态与操作区可分层，但不应散落到页面两侧。
- 宽屏优先让棋盘使用可用高度，不能只增加无目的黑色留白，也不能把“小型中央工作区”当成通用模板。
- “主要内容位于首屏”意味着先压缩无效装饰、空白和外围容器，不意味着通过缩小棋盘、文字或按钮强行塞入视口。
- 小棋盘设置合理上限，高密度棋盘可随视口继续增长；不同棋盘尺寸不得共用一个僵硬的固定上限。
- 小棋盘的精致感来自构图、留白和层级，不来自把单格放大成按钮；高密度棋盘则优先获得可用高度，两者分别设定尺寸范围。
- 移动端可使用同样的信息顺序；本规范不要求在每次桌面改动时同步重构移动端。

### 桌面三档布局原则

桌面验收固定覆盖三档：1920×1080、1440×900、1024×768。用可控制的响应式规则（clamp + vw/dvh 中值）覆盖三档，不为单档写大量硬编码。

- 1920×1080：提高棋盘与核心内容的屏占比；HUD 与工具区保持克制不拉宽；规则说明不与棋盘争夺视觉权重；棋盘放大必须带 vw/dvh 中值约束，不得导致低分辨率溢出。
- 1440×900：标准桌面基准，棋盘、工具与提示保持平衡；不得因为照顾 1920 而让 1440 拥挤。
- 1024×768：允许工具区收紧、次要说明降级、非核心标签减少；禁止隐藏核心操作、禁止按钮不可点、禁止用横向滚动解决布局问题；1024 收口不等于启动移动端重构。

## 6. 边框、圆角、阴影与发光

- 边界用于分层、分区和焦点；跨区域或关键边界强于普通内部边界。
- 圆角表达产品质感，但高密度棋盘的格子圆角与间距必须足够小，让区域首先读成连续形状，而不是一组彼此分离的彩色按钮。
- 阴影只服务工作区与浮层分层，避免多层厚重卡片堆叠。
- 发光不承担主要识别职责。奖励星点、完成和焦点可使用短暂、有限光晕；高频重复元素不得全部发光。
- 胶囊不是默认控件形状。主 HUD、普通工具按钮和状态区应先依靠信息关系与位置建立层级，不能依赖一排微型灰色胶囊。

### 玩法图形与 Star Line 家族规则

- One Line 四玩法必须先靠图形结构区分：经典是带编号的连续曲线路径；隐迹连线是被遮蔽的断续路径与少量数字线索；八向连线使用明确的斜向折线与方形节点；传送门使用成对门环和跨越间隙的跳转。
- Hidden 的玩家名称统一为「隐迹连线」；代码模式 ID `hidden` 保持不变。
- Star Line 使用共同的星域框架作为家族母视觉。单星使用单核心星点、单环结构和冷紫蓝；双星使用成对星点、配对连线和暖玫红。
- 单星 / 双星各自的强调色必须贯穿玩法 Tab、主 CTA、关卡节点、连接线、选中、悬停与键盘焦点；锁定统一回到中性灰，不继承玩法高亮。
- 金色保留给真实星点、奖励和完成结果；青绿色保留给 One Line 经典玩法。Star Line 目录不以金色或青绿色承担普通选中状态。

## 7. 游戏棋盘通用规则

- 棋盘必须是页面主视觉，缩小或眯眼时仍能读出主要结构。
- 未处理、已处理、目标、冲突必须一眼可区分。
- 区域类玩法至少同时使用区域底色、相邻差异和连续边界三种线索。
- 同一区域内部边界必须明显弱于跨区域边界；跨区域轮廓应连续闭合，区域颜色不能退化成逐格装饰。
- 区域底图与交互格应按视觉职责分层：先读完整区域形状，再用弱网格定位单格；单格不得各自使用卡片渐变、独立粗边和大圆角来模拟区域。
- 高密度标记应服务排除或确认，不得形成比空格更强的视觉噪音。
- 玩法层可定义自己的状态排序；例如 Star Line 固定为：`星点 > 空格 > X`。
- HUD 是完整但克制的玩家信息栏：导航、关卡身份、规则和进度形成稳定关系；开发入口必须独立降权，不得混入玩家主信息。
- 底部状态应紧贴棋盘并保持稳定宽度；操作按钮可以有清楚的品牌色和可用状态，但不应被包进横跨页面的空工具框。

## 8. 可访问性与验收

- 关键文字与状态数字使用主 / 次文字层级，不能依赖低对比小字。
- hover 不是唯一反馈；选中、启用和冲突在触控或键盘环境也必须有可见状态。
- 不恢复产品已移除的游戏键盘操作；键盘支持以当前实际交互范围为准。
- reduced-motion 下保留静态状态和结果，不依赖动效传达意义。
- 常见桌面视口中，棋盘、状态和必要操作应同时可用；验收时优先删除无效留白与装饰，在此基础上让棋盘获得尽可能多的可用高度。
- 棋盘页至少用 1920×1080、1440×900、1024×768 三档桌面尺寸检查；高密度玩法还需覆盖空盘与大量标记状态。

### 证明驱动教学

Star Double Lv.2–9 的 Guided / Transfer 使用当前盘面动态生成的证明。界面必须遵守：

- 棋盘仍是第一视觉焦点；教学卡只说明本课主题、当前观察对象和动作类型。
- 教学卡不得遮挡核心棋盘区域。在教学步骤进行中，教学卡应始终可见但不压盖棋盘操作区。
- 观察范围与推理依据使用不同视觉语义，并且都不能伪装成最终答案。
- Guided 与 Transfer 都不高亮 `derivedTargets`；Transfer 仍保留观察对象和”标 X / 放置星星”的明确动作说明。
- `place-star` 的玩家语言是”在确定的位置放置星星”；`eliminate` 是”把不能放星的位置标成 X”。动作类型应在教学卡上动态更新，不固定为单一文案。
- 没有符合合同的有效证明时，棋盘输入必须暂停并显示错误状态；不能用空目标、任意规则或静态坐标继续教学。
- 非法操作不改盘、不推进步骤、不自动显示答案；盘面变化后旧证明立即失效。错误反馈应显式说明原因（如”这里不能放星”或”这里不需要排除”），不静默拒绝。
- 依据、观察和目标的差异不能只靠颜色；应同时依靠边界、层级或标记形态。
- INTRO 必须等待玩家手动确认，不能自动跳过；玩家确认后进入 SETUP、GUIDED 或 AUTONOMOUS。SUMMARY 表示课程完成状态，当前版本进入 SUMMARY 后立即写入完成记录并结束教学卡，没有 SUMMARY 手动确认按钮。
- 教学卡层级：INTRO 卡 > 教学步骤卡（SETUP/GUIDED/TRANSFER_PRACTICE）。SUMMARY 当前不保留可见教学卡；未来若改为可见总结页，必须另行设计和测试。
- 不增加复杂阶段进度条或步骤计数器；教学进度通过教学卡内容变化自然表达。
- E2E proof bridge 是测试接口，不属于玩家 UI；production build 中不得存在。

## 9. Motion 与反馈

Motion 的唯一来源是 `src/config/motionPresets.js`（JS）与 `src/index.css` 的 `--motion-*` 变量（CSS），两者语义一一对应。新 UI 改动必须复用这些 token 与公共预设，禁止在组件内新增任意毫秒字面量、easing 曲线或 spring 参数。

### Duration token

只使用五档，stagger 不是第六档：

| Token | 值 | 用途 |
| --- | --- | --- |
| Instant | 100ms | 格子按压等即时反馈 |
| Fast | 160ms | reduced-motion 下的 opacity 保留档、轻提示 |
| Base | 240ms | 常规面板、数值变化 |
| Emphasis | 420ms | 需要被注意到的状态进入 |
| Ritual | 800ms | 完成仪式类一次性动画 |

### Easing

只建立两种：Standard `cubic-bezier(0, 0, 0.2, 1)` 为默认；Emphasized `cubic-bezier(0.2, 0.75, 0.25, 1)` 用于需要强调的进入。

### Spring

只建立两组：Gentle（stiffness 300 / damping 22 / mass 0.6）用于普通一次性面板进入；Celebrate（stiffness 400 / damping 12 / mass 1）仅用于胜利星级、解锁徽标和重要奖励。高频格子、HUD、按钮、撤销和错误反馈禁止使用 spring。

### Stagger

固定步进 60ms，总 stagger 不超过 300ms；通过 `staggerDelay(index)` 计算，不写分散的延迟字面量。

### 状态语义

- 面板 / 背景：`winPanelEnter`、`backdropEnter`；Toast：`toastEnterExit`；解锁奖励：`unlockBadgeEnter`。
- HUD 数值变化：`hudValuePulse`；连击里程碑：`comboMilestonePulse`；生命扣除使用错误语义色的短 pulse。
- 教学卡切步：`teachingStepFade`（Base opacity crossfade，极轻微位移）。
- 棋盘：按压 `cellTap`、错误 `errorShake`；错误反馈用位移抖动而非常驻动画，且不依赖 spring。
- Star Line 撤销复用标记的现有 exit/enter 反馈，被撤掉的标记走 Fast exit overlay，不新增第二套撤销动画。
- 动画表达“发生了什么”的辅助语义，状态本身（错误文字、冲突边界、完成状态、数值）必须不依赖动画成立。

### Reduced-motion

- 全局入口：`main.jsx` 的 `MotionConfig reducedMotion="user"` 负责 Motion 组件；CSS 侧由 `index.css` 的全局 `prefers-reduced-motion` 基础与各区块规则负责；Tailwind `active:scale` 按压缩放在 reduced-motion 下以严格限定的 `!important` 关闭（components 层在构建产物中先于 utilities 层，不加 `!important` 会被 utility 覆盖）。三者各自受控，不能只依赖 MotionConfig。
- reduced-motion 下取消位移、缩放、shake、spring 弹跳和循环动画；页面进入使用独立的 opacity-only keyframe，面板与 Toast 使用 `fadeOnly`，均为 Fast 160ms 纯 opacity。
- 错误文字、冲突边界、完成状态和数值必须保留；声音不自动关闭。

### 声音原则

- 所有音效经 `soundEngine.js` 的 `safeTone` 合成，不加载音频文件、不引入音频依赖、不加背景音乐。
- 事件使用语义函数（放置星点、标 X、冲突、撤销、解锁、完成、失败、奖励），组件不直接写频率参数。
- 音效是反馈的增强层，不是状态的唯一表达；静音或 reduced-motion 下玩法信息必须完整。

### 禁止的装饰动画

- 无限循环的呼吸、漂浮、闪烁不得用于高频元素（格子、HUD、按钮）。
- 不以纯装饰动画拖延玩家操作节奏；仪式类动画一次性完成且可降级。
- 不得在组件内绕过公共 token 自行发明时长、曲线或 spring。

## 10. 令牌与改动流程

基础 CSS 语义令牌定义在 `src/index.css`：背景 / 表面 / 工作区 / 棋盘、主次文字、状态色、边界、圆角、间距、阴影与焦点光晕。玩法专属变量应建立在这些令牌之上，不能冒充全产品规则。

正式玩法的玩家可见规则说明以 [`docs/game-explanation-system.md`](./game-explanation-system.md) 和 `src/config/gameExplanations.js` 为准。UI 改动不得在组件内重新发明核心玩法用语。

后续每次 UI 改动都应：

1. 判断是否涉及本规范，并优先复用现有令牌。
2. 新增可复用规则时同步更新本文件。
3. 明确“本次落地页面”与“未来适用范围”。
4. 避免在模块内部堆积孤立的颜色、字号或状态逻辑。
5. 在最终汇报中说明调整了哪些产品级规则和哪些页面实际落地。
