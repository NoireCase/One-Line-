# Linebook UI 设计规范

> 本文定义 Linebook 的产品级界面规则。Star Line 是第一套完整落地案例；规则适用于后续页面和玩法，但不要求旧页面在一次改动中全部迁移。

## 1. 视觉定位与优先级

Linebook 是“夜空中的谜题册”：深色外壳提供安静的氛围，谜题工作区提供足够明亮、稳定的阅读面。背景装饰只能烘托，不能压过关卡信息、棋盘或操作反馈。

- 游戏内容始终是页面第一视觉焦点，棋盘类玩法尤其如此。
- 夜空背景以近乎纯净的深色空间为主；少量、不规律的星点可以存在，但重复方格、成片模糊光斑和装饰纹理不得成为默认语言。
- 每种玩法可有自己的强调色，但需沿用同一套中性色、文字层级、边界和状态语义。
- 不以强发光、厚阴影或高饱和颜色替代信息结构。

## 2. 页面亮度层级

深色主题必须形成清楚的阶梯，不能把所有内容压在相近暗灰区间。

| 层级 | 职责 | 不能混同的对象 |
| --- | --- | --- |
| 页面背景 | 夜空氛围与无关留白 | 工作区、可读文字 |
| 内容层 | 普通页面卡片和导航 | 棋盘底板 |
| 游戏工作区 | 让棋盘从背景中站出来 | 页面背景、工具区 |
| 棋盘格与可操作内容 | 支持扫描和推理 | 已处理标记 |
| 已处理 / 降权信息 | 保留可确认性，不抢答题焦点 | 当前可操作信息 |
| 关键结果 | 完成、奖励、真实错误和焦点 | 常规装饰 |

棋盘底板必须比页面背景和普通内容层更清楚；未处理格必须比已排除标记更容易发现。

## 3. 颜色与状态

### 颜色规则

- 使用语义令牌：背景、表面、文字、边界、奖励、成功、警告、错误、焦点，而不是在组件内随意新增近似颜色。
- 金色只用于奖励、星点和完成等关键结果，不用于大面积底色。
- 错误红只用于真实冲突或失败；普通状态、进度和区域色不得伪装成错误。
- 关键状态不得只靠颜色表达，必须同时有文字、图形、边界或位置变化。
- 相邻区域或状态应同时具备色相 / 明度差和边界差，不能只提高饱和度。

### 状态权重

1. 当前目标、关键结果、焦点信息。
2. 当前可操作信息。
3. 已完成或已处理信息。
4. 禁用与背景性说明。

已处理信息通常应降权，不能比待处理信息更抢眼。悬停、选中和教学引导必须可见，但不应覆盖真实冲突反馈。

“降权”不等于隐藏。高密度排除标记需要比空格安静，但玩家在正常观看距离下仍应无需停顿即可确认其存在。

### 锁定内容层级

- 关卡选择页的视觉权重排序：当前推荐关 > 已解锁未完成 > 已完成可重玩 > 未解锁。
- 未解锁关必须明显降权，不得形成“锁墙”。V3.1 目录通过低明度编号、弱边界和不可操作性共同表达，不另加重复锁图标或「未解锁」文字。
- 降权不得改变实际解锁条件、进度与关卡顺序的准确表达。

## 4. 排版与信息层级

| 层级 | 用途 | 桌面建议 |
| --- | --- | --- |
| 页面标题 | 页面或玩法入口标题 | 24px 以上，强对比 |
| 模块标题 | 章节、面板、结果标题 | 18–20px，强对比 |
| 关卡主信息 | 玩法名、关卡名 / 编号 | 14–16px，主文字 |
| 状态数字 | 进度、计数、结果 | 至少与关卡主信息等强，数字可更大 |
| 辅助标签 | 棋盘规格、规则类型 | 12px 以上，次文字 |
| 正文 / 按钮 | 可操作文字与说明 | 13px 以上 |
| 次要说明 | 非关键提示 | 12px 以上 |

11px 以下文字不得承担玩家必须读取的规则、状态或按钮含义。灰色只用于次信息，不能替代层级设计。

玩家可见最小字号按语义执行，不做全局统一放大：

- 玩家必须阅读的信息（核心操作名、当前关卡信息、进行中的关键状态、首次教学提示）：≥12px。
- 状态数字旁的单位、结果数据的标签、导航类标签：≥11px。
- 9–10px 只允许用于不承担独立含义的内容（瞬时确认提示、hover 辅助说明、开发调试标记）；开发 / 测试内容不为了统一而放大。
- 单项调整必须有语义依据，不允许通过统一放大让卡片、按钮和布局整体膨胀。

### 信息去重与表面职责

同一信息在屏幕上只保留一个主要来源；其余位置删除、缩短或降级，不通过改写措辞保留所有副本，也不把删掉的信息用 tooltip 塞回来。

- 首页：只回答「两个家族是什么、我能继续什么」。不放选择指令、家族内玩法索引或重复规则；继续入口必须显示玩法名称与关卡号等存档上下文（只读现有存档字段推导，不改存档结构）。
- 关卡选择页：玩法切换只显示玩法名；当前页 / 总页数只在十关网格右下方显示一次，不重复棋盘尺寸、完整规则或完成进度。
- HUD：只保留进行中必须持续查看的信息（导航、关卡身份、规则类型、进度、生命 / 资源）；已固定在棋盘旁的状态（如路径进度）不在 HUD 重复。
- 棋盘旁状态：紧贴棋盘，只保留与盘面直接相关的一行进度。
- 教学区：游戏目标与规则在首次教学或明确规则区说明，HUD 不重复整句规则。
- 结果面板（Win / Lose）：只展示结果、关键数据与下一步动作，不重新完整讲规则；规则完成语义用一处徽标或一句话表达。

## 5. 间距与布局

- 首页的主内容必须落在单一、边界明确的前景表面上；卡片是该表面的内部结构，不得直接漂浮在页面背景上。首页前景容器与视口之间保留 8–12px 的「有意画框」缝隙，容器描边强于普通内部边界一档，并带极淡内描边与顶部边缘光。
- 关卡选择页不使用页面级大边框：全屏连续的夜色背景即页面本身，无外层圆角边框、无内描边、无顶部边缘光、无画框式缝隙、无替代性暗线或外层阴影，页面四边不得出现细线或画框效果。首页与关卡选择页必须直接消费 `--linebook-night-background`，共享同一片夜。
- Linebook 的首页外壳、简化卡片与插画底面由 `--linebook-shell-*`、`--linebook-card-*`、`--linebook-art-*` 和 `--linebook-cream` 公共 token 定义。首页是这些 token 的视觉基准；关卡页的章节承载面与关卡格只能以透明度和层级组合形成“内页”变体，不能另写一组近似硬编码颜色。
- 页面背景只保留低对比的大尺度明暗变化，不使用高频重复方格、密集星点或可被误读为内容边界的纹理。
- 游戏页建立连续中轴：`关卡信息 → 棋盘 → 状态反馈 → 操作`。
- 首页的「Linebook 标题 + 双家族卡」是一个饱满的展示块：卡片高度随视口增长（clamp + vh 中值），插画区是卡片上半部的主角，插画图形同比放大并居中，卡片内部留白随高度重新分配。卡片与容器允许顶部极细内高光、柔和外阴影，以及插画区极淡的家族色径向光（One Line 青、Star Line 紫），保持克制不要塑料感；入口按钮样式不随卡片高度变化。
- 棋盘与状态区保持紧邻；状态与操作区可分层，但不应散落到页面两侧。
- 宽屏优先让棋盘使用可用高度，不能只增加无目的黑色留白，也不能把“小型中央工作区”当成通用模板。
- “主要内容位于首屏”意味着先压缩无效装饰、空白和外围容器，不意味着通过缩小棋盘、文字或按钮强行塞入视口。
- 小棋盘设置合理上限，高密度棋盘可随视口继续增长；不同棋盘尺寸不得共用一个僵硬的固定上限。
- 小棋盘的精致感来自构图、留白和层级，不来自把单格放大成按钮；高密度棋盘则优先获得可用高度，两者分别设定尺寸范围。
- 移动端可使用同样的信息顺序；本规范不要求在每次桌面改动时同步重构移动端。

### 桌面三档布局原则

桌面验收固定覆盖三档：1920×1080、1440×900、1024×768。用可控制的响应式规则（clamp + vw/dvh 中值）覆盖三档，不为单档写大量硬编码。

- 1920×1080：提高棋盘与核心内容的屏占比；HUD 与工具区保持克制不拉宽；规则说明不与棋盘争夺视觉权重；棋盘放大必须带 vw/dvh 中值约束，不得导致低分辨率溢出。
- 1440×900：标准桌面基准，棋盘、工具与提示保持平衡；不得因为照顾 1920 而让 1440 拥挤。
- 1024×768：允许工具区收紧、次要说明降级、非核心标签减少；禁止隐藏核心操作、禁止按钮不可点、禁止用横向滚动解决布局问题；1024 收口不等于启动移动端重构。

## 6. 边框、圆角、阴影与发光

- 边界用于分层、分区和焦点；跨区域或关键边界强于普通内部边界。
- 圆角表达产品质感，但高密度棋盘的格子圆角与间距必须足够小，让区域首先读成连续形状，而不是一组彼此分离的彩色按钮。
- 阴影只服务工作区与浮层分层，避免多层厚重卡片堆叠。
- 发光不承担主要识别职责。奖励星点、完成和焦点可使用短暂、有限光晕；高频重复元素不得全部发光。
- 胶囊不是默认控件形状。主 HUD、普通工具按钮和状态区应先依靠信息关系与位置建立层级，不能依赖一排微型灰色胶囊。

### 玩法图形与 Star Line 家族规则

- One Line 四玩法必须先靠图形结构区分：循序寻踪是连续流动路径；隐迹寻踪使用缺失区、错位回声与单一推进关系；八向寻踪使用 3—4 次主要方向变化的连续折角；跃迁寻踪使用两枚完整门环、入口/出口和轻量空间桥接。签名不使用编号节点、棋盘、坐标或真实关卡预览。
- One Line 家族保持共同夜色、奶油标题和金色终点，并使用四组多角色支流色：循序寻踪为薄荷青绿（`#55D6C1 / #A6F0E2 / #256B65`）；隐迹寻踪为雾蓝灰加紫灰回声（`#8DAFCB / #D4E2EC / #4F657B / #A49BCB`）；八向寻踪为钴蓝加方向青（`#667FF2 / #B8C6FF / #354590 / #62D0E4`）；跃迁寻踪为更明确的翡翠绿（主路径 `#32C777`、高光 `#A3F1BF`、深层 `#145C39`、空间辅助 `#287C58`），完整双门环使用 `#F0A64B / #FFD18A`。色彩只进入当前 tab、章节身份、规则重点、难度、推荐关和极小进度强调，不覆盖普通关卡或页面背景。
- Star Line 继承首页的深紫空间、稀疏节点、细关系线与金色机制焦点，但不复制首页插画。单星使用柔和紫色（主色 `#8B72D9`、高光 `#D5C8FF`）；双星使用玫紫色（主色 `#C45B8E`、高光 `#F0B2CF`）。推荐关发光半径与透明度跨玩法保持一致，仅替换色相并做必要的感知校正。
- 未来扩展规则（只沉淀，不制作页面）：
  - 日月、黑洞、三星、星轨与引力继续复用 Star Line 页面骨架和规则签名画布，只填写家族内部的主题变量与节点关系，不重新设计关卡卡片和布局。
- 主题变量体系（CSS custom properties，按 mode class 切换）：
  - `--level-accent`（RGB）：家族强调色，驱动当前 tab 顶边、章节符号、推荐关光晕、完成格描边和箭头 hover 色
  - `--level-accent-strong`：浅色强调色（hex），用于当前 tab 文字、推荐关编号
  - `--level-rec-border/--level-rec-bg/--level-rec-bg-peak`：推荐关结构边缘与底面提亮参数，跨玩法共用同一套层级，只换色相
- One Line 四个玩家名称统一为「循序寻踪 / 隐迹寻踪 / 八向寻踪 / 跃迁寻踪」；代码模式 ID `classic / hidden / diagonal / portalClassic`、路由、存档 key 与关卡规则保持不变。
- Star Line 使用「节点网络＋星核关系」作为家族母视觉。单星以普通节点和关系线向一个金色星核汇聚，表达「单核汇聚」；双星以两个等权金色星核和共享节点链组成一个完整网络，表达「双核协作与共享关系」。规则签名不使用轨道、眼形、多边形地块、棋盘切片或真实关卡预览。
- 单星 / 双星各自的强调色必须贯穿玩法 Tab、关卡格、选中、悬停与键盘焦点；锁定统一回到中性灰，不继承玩法高亮。
- 金色保留给 Star Line 星核、真实星点、奖励和完成结果，是统一的机制焦点；青绿色保留给 One Line 经典玩法。Star Line 目录不以金色或青绿色承担普通选中状态。

### 关卡选择页 V3.1

关卡选择页是 Linebook 封面进入后的章节内页，不是地图、路线、后台目录或章节管理页。

- 页面以全屏连续夜色背景承载（不使用页面级大边框）；同一块无硬边的低亮章节材质从品牌区连续延伸到进度区，把品牌、玩法索引、难度、关卡与进度组织成一页。章节材质直接复用首页外壳 token，但去掉首页的封面画框与圆角，形成「封面 → 内页」关系。
- 顶部只显示玩法家族品牌，其下是只含玩法名的轻量切换。品牌区与切换区之间不使用通栏细分隔线；切换的当前玩法使用浅层内页索引片和顶部短边强调，不使用网页导航式下划线。
- 关卡浏览组件固定为 `章节信息 → 五列两行十关网格 → 上一页｜当前页 / 总页数｜下一页`。三段放在同一块低亮、圆润、带极细内描边的共享章节材质中，网格始终是第一视觉主体，组件整体居中且页面本身不滚动；tab 与章节主体之间不保留大块死空白。
- 章节头部只出现一次中尺度「规则签名」，并与子玩法名称、难度共同组成章节身份：规则签名在左，子玩法名称与难度形成右侧标题栈，三者语义不得错位。规则签名使用统一画布、统一位置和统一线条层级；它比单个关卡编号更有存在感，但必须明显弱于 5×2 网格和推荐关。
- 规则签名的换章周期与完成态、重玩态和浏览窗口更新解耦：只在从首页进入章节或真正切换玩法时触发，点击当前玩法、从游戏返回同一玩法、翻页及 `ceremony / sealed / replay` 更新均不重播。六玩法均以 800ms 完成且标题栈纳入同一周期：循序寻踪为 `0–80 起点 / 80–620 主路径 / 620–720 场域与方向 / 720–800 终点`；隐迹寻踪为 `0–80 起点 / 80–300 左段 / 300–400 渐隐 / 400–610 顺序回声 / 610–740 右段 / 740–800 终点`；八向寻踪为 `0–80 起点 / 80–650 折角主路径 / 650–730 方向场 / 730–800 终点`；跃迁寻踪为 `0–80 起点 / 80–250 左段 / 250–360 入口门环 / 360–470 桥接与出口 / 470–700 右段 / 700–800 终点`；单星为 `0–100 普通节点 / 100–480 普通关系 / 480–650 核心关系 / 650–750 星核点亮 / 750–800 稳定收束`；双星为 `0–100 普通节点 / 100–360 第一组关系 / 360–560 第二组关系 / 560–680 共享关系 / 680–760 双核错峰点亮 / 760–800 稳定收束`。不使用 hover 重播、循环待机或退出副本；隐迹动画任意时刻只有一个推进头。reduced-motion 首帧直接显示完整签名与推荐关静态高亮，不以极短时长模拟完成态。
- 关卡选择页字阶跨四玩法统一：家族标题 `ONE LINE` 在 1920/1440 为 20–22px、1024 不低于 18px；完整玩法名为 28–32px、1024 不低于 24px；当前玩法 tab 与难度为 14–16px、1024 不低于 13px；页脚当前完成数为 22–24px，总数与分隔符为 12–13px。玩法名统一使用奶油白，难度使用当前玩法高光色；不得为单一玩法另设字号。
- One Line 的经典与隐迹章节使用同源的低明度规则场域：两条克制边界、低亮底路、主路径、方向与单一金色终点共同建立身份体量，图形末端与标题层级轻微交叠，不使用独立徽章外轮廓、工程标尺或信息横幅。经典保持连续路径；隐迹必须让遮蔽同时作用于路径与场域，不能只把经典路径的一段改成虚线。场域静态完成度高于线稿图例，但视觉重量始终低于 5×2 网格和唯一推荐关。
- 六种规则签名只改变图形语法：经典为有起终点与方向性的完整连续线；隐迹保留同源线条但中段被稳定遮蔽；八向使用明确的连续斜向折角；传送门使用成对门环、入口/出口与跨越弧；单星使用单核汇聚的节点网络；双星使用双核共享的完整节点网络。它们是抽象规则身份，不使用真实谜面、真实节点布局或关卡解法，也不进入每张关卡格、背景水印或玩法专属页面构图。
- 分页箭头属于章节页脚，使用与关卡格同源材质、细描边和线性折角；不得使用实心网页分页三角。左右按钮与页码组成稳定三列，边界禁用态不改变页码和网格位置。
- 关卡格使用首页入口卡的安静内页材质，不复制首页封面构图。编号回到卡片几何中心，卡内不使用顶部表单线、档案侧边或玩法装饰。三态只通过数字明度、卡片底色和边框分级；当前推荐关是唯一允许持续克制辉光的关卡。
- 所有玩法统一按线性关卡顺序每十关一页：`1–10 → 11–20 → …`，总页数为总关卡数除以十向上取整。最后一页不足十关时只渲染真实关卡，不补锁定卡、占位卡或敬请期待内容；空余位置由固定 5×2 网格画布自然保留。
- 页面章节信息来自玩法现有章节配置。单页跨越多个已配置章节时明确组合对应章节名，不根据页面第一关临时推断，也不把某一玩法的章节名称复用于其他玩法。
- Portal 继续保留空难度名和同一垂直锚点，但其 30 个真实关卡与其他玩法一样分为三页。
- 当前推荐关仍为「存档关优先，否则第一个已解锁未完成关」，使用主题描边、轻微放大和克制呼吸作为唯一第一操作焦点；章节身份区保持第二层级。推荐关在所有玩法间共用同一发光半径、发光透明度、边框亮度与背景提亮幅度（高明度色相可做小幅感知校正），玩法之间只改变色相，不改变视觉强度。
- 普通四态为：已完成、当前推荐、已解锁未完成、未解锁。编号永远是格内第一视觉信息，不添加任何玩法内图形装饰（不恢复波浪、星点、圆环、斜线等格内 motif）。玩法差异仅通过家族色温表达，编号大小跨玩法一致。
- 页码与上一页、下一页按钮共同位于章节页脚；当前页使用奶油主数字、总页数降级，整体与章节信息及网格共用同一垂直轴。不得添加全局完成进度、分页圆点、滚动提示、底部难度栏、Continue CTA 或解释模块。
- 浏览只接受水平方向：分页按钮每次一页；触摸板只响应明确横向的双指 wheel；鼠标按住横向拖动达到阈值后在松开时翻一页；键盘焦点使用左右方向键。纵向 wheel、纵向拖动与上下方向键不翻页。
- 触摸板事件串以“连续输入结束”为手势边界：达到阈值后锁定整串 wheel 及惯性事件；鼠标从按下到松开为一个手势；页面切换期间拒绝叠加输入。任一手势最多翻一页，新手势需在上一手势结束且切换完成后才能生效。
- 分页箭头默认完全静止，hover 只允许轻微亮度或描边变化；实际按下按钮时使用 Fast（160ms）的一次性 1px 方向位移与轻微缩放。触摸板或拖动翻页不触发按钮按压反馈；第一页上一页、末页下一页禁用且不播放成功反馈。
- 完整玩法完成态按稳定 mode ID 隔离：`classic`、`hidden`、`diagonal`、`portalClassic`、`starSingle`、`starDouble`，不得用一个页面全局完成值污染其他玩法。
- 首次完整玩法通关且由本次胜利流程明确返回时进入 `ceremony`：从最后十关反向染金，按约 450ms / 页回翻到 1–10，绘制封存金线、显示「已通关」并有限引导下一未完成玩法。任意操作可跳过。
- 仪式自然结束、跳过或 reduced-motion 降级时，立即写入独立 UI key `cg_level_select_completion_ceremony_v1`。该 key 只记录已播放仪式的玩法 ID，不修改业务进度、存档 schema、奖励或解锁。
- 已完成的老存档没有本次首次完成事件时直接进入 `sealed`，并可同步标记仪式已处理；不得在升级后突然补播完整仪式。
- `sealed` 固定显示第一页 1–10：整组卡片以深色主体、浅金编号、低透明度金色细边与克制暖金内层高光表达首次整体通关，不使用大面积纯金填充、持续闪烁或持续发光。网格外继续使用与卡片圆角一致、留有稳定内距的低透明度细金线完成框，不得形成粗横条、粗竖条或表格感。右下角隐藏分页箭头，显示静止的双层入口「已通关 / 点击重玩」，前者为主状态、后者为弱提示；入口具备 pointer、hover、focus-visible 与一次性 pressed 反馈，点击后先打开确认框，不直接进入关卡。
- 重玩确认标题为「{玩法名}已通关」；正文固定为「进入重玩模式后，可自由选择任意已完成关卡。通关记录不会清除。」；操作为「进入重玩」和「取消」。对话框必须有 dialog 语义、焦点圈定、Esc 取消和关闭后焦点返回。
- 正常首次推进的当前关使用玩法色推荐描边、提亮背景与克制辉光，并且只在右上角显示金色星星；金色星星不得表示首次已通关、二次当前或二次已通关。
- 确认后进入持久化 `replay`：首次定位第一页并把规范关卡顺序中第一个尚未二次通过的真实关卡作为当前推荐，恢复分页箭头、所有首次已完成关点击与当前页 / 总页数。当前重玩关复用玩法色推荐高亮，编号保持玩法色，并在右上角显示玩法族专属 SVG；不增加「当前 / 继续 / 重玩中」等文字。
- 已二次通关关卡回到普通可玩卡片基础材质，编号变为金色，右上角保留玩法族专属 SVG；不增加完整金色外框。全部二次通关后推荐指针为空，所有真实关卡保持金色编号与对应 SVG，继续允许分页，不循环回第 1 关，也不恢复 `sealed`。
- One Line 重玩标识复用首页 One Line 进入按钮的折线 SVG，覆盖 `classic`、`hidden`、`diagonal`、`portalClassic`；Star Line 重玩标识复用首页 Star Line 进入按钮的 SVG，覆盖 `starSingle`、`starDouble`。两种几何不得混用；SVG 类型只由集中 modeId→玩法族映射在渲染时推导，不写入存档。
- `sealed` 与 `replay` 是互斥状态：前者表达整个玩法首次完成的成就总览，后者表达独立二次进度。卡片交互优先级固定为 `pressed > hover / focus > 当前重玩推荐 > 二次通过金色编号 > 玩法族 SVG > 基础卡片`；SVG 默认静止，仅在真实 hover、focus 或按下时由卡片提供短反馈。
- `replay` 使用独立版本化 key `cg_level_select_replay_v1`，按稳定 mode ID 分别保存 `replayActive`、`replayCompletedLevelIds` 与 `lastReplayPage`。每次写入基于最新存储值只合并当前玩法节点；当前推荐由规范关卡顺序与完成 ID 列表推导，避免双重真相并兼容自由选关形成的空洞。切换玩法或玩法族、返回首页、路由变化、刷新和重新载入均不得清除；完成全部二次通关也保留记录。
- 进入 replay、确认对话框和重玩已完成关均不得清除 completed / unlocked、改变首次解锁顺序、重复发放首次奖励或重播完整仪式。重玩存档异常只能降级为空重玩记录，不得影响首次通关存档。
- reduced-motion 直接从 ceremony 落到 sealed；推荐关、完成金色、封存线和引导的静态语义仍需保留。
- 正式验收固定覆盖 1920×1080、1440×900、1280×720、1024×768：五列两行、全部核心操作、无整体横纵滚动，并检查 60 / 30 / 13 关分页、末页真实关卡、水平 wheel、鼠标拖动、边界、章节同步、sealed、确认框、replay 和玩法隔离。
- 章节承载面必须覆盖从品牌到进度的完整阅读路径，不能只在网格背后制造一块发光舞台。材质靠同源底面、连续纵向层级和开口渐隐建立，不使用家族色大面积染色；玩法色只进入当前索引、难度标记、关卡状态边缘和交互焦点。
- 章节头部、网格和章节页脚使用同一垂直中轴与共享底面，不能分别采用左对齐、居中、右对齐三套阅读轴。共享章节材质通过内容聚合解决宽屏空旷，不靠放大十个空卡片、中央 glow 或背景图案填充。
- 1920×1080 档限制关卡格最大尺寸，通过章节头部与页脚的完整结构占据页面中心主要区域；1440×900、1280×720 和 1024×768 只收紧章节内间距与关卡格，不改变三段顺序。
- 未来 Star Line 玩法继续复用规则签名画布，以节点、关系与机制焦点表达差异；只新增图形语法与家族主题变量，不修改关卡格、章节材质、标题栈或页面布局。
- 禁止地图、星轨、曲线节点、路线、左侧章节栏、底部页签 / 难度栏、CTA、大型说明区、独立装饰区和跨格主题图案。禁止页面级大边框、画框缝隙、内描边、顶部边缘光。禁止难度标题下方的小曲线、玩法签名和格内玩法水印。

## 7. 游戏棋盘通用规则

- 棋盘必须是页面主视觉，缩小或眯眼时仍能读出主要结构。
- 未处理、已处理、目标、冲突必须一眼可区分。
- 区域类玩法至少同时使用区域底色、相邻差异和连续边界三种线索。
- 同一区域内部边界必须明显弱于跨区域边界；跨区域轮廓应连续闭合，区域颜色不能退化成逐格装饰。
- 区域底图与交互格应按视觉职责分层：先读完整区域形状，再用弱网格定位单格；单格不得各自使用卡片渐变、独立粗边和大圆角来模拟区域。
- 高密度标记应服务排除或确认，不得形成比空格更强的视觉噪音。
- 玩法层可定义自己的状态排序；例如 Star Line 固定为：`星点 > 空格 > X`。
- HUD 是完整但克制的玩家信息栏：导航、关卡身份、规则和进度形成稳定关系；开发入口必须独立降权，不得混入玩家主信息。
- 底部状态应紧贴棋盘并保持稳定宽度；操作按钮可以有清楚的品牌色和可用状态，但不应被包进横跨页面的空工具框。

## 8. 可访问性与验收

- 关键文字与状态数字使用主 / 次文字层级，不能依赖低对比小字。
- hover 不是唯一反馈；选中、启用和冲突在触控或键盘环境也必须有可见状态。
- 不恢复产品已移除的游戏键盘操作；键盘支持以当前实际交互范围为准。
- reduced-motion 下保留静态状态和结果，不依赖动效传达意义。
- 常见桌面视口中，棋盘、状态和必要操作应同时可用；验收时优先删除无效留白与装饰，在此基础上让棋盘获得尽可能多的可用高度。
- 棋盘页至少用 1920×1080、1440×900、1024×768 三档桌面尺寸检查；高密度玩法还需覆盖空盘与大量标记状态。

### 证明驱动教学

Star Double Lv.2–9 的 Guided / Transfer 使用当前盘面动态生成的证明。界面必须遵守：

- 棋盘仍是第一视觉焦点；教学卡只说明本课主题、当前观察对象和动作类型。
- 教学卡不得遮挡核心棋盘区域。在教学步骤进行中，教学卡应始终可见但不压盖棋盘操作区。
- 观察范围与推理依据使用不同视觉语义，并且都不能伪装成最终答案。
- Guided 与 Transfer 都不高亮 `derivedTargets`；Transfer 仍保留观察对象和”标 X / 放置星星”的明确动作说明。
- `place-star` 的玩家语言是”在确定的位置放置星星”；`eliminate` 是”把不能放星的位置标成 X”。动作类型应在教学卡上动态更新，不固定为单一文案。
- 没有符合合同的有效证明时，棋盘输入必须暂停并显示错误状态；不能用空目标、任意规则或静态坐标继续教学。
- 非法操作不改盘、不推进步骤、不自动显示答案；盘面变化后旧证明立即失效。错误反馈应显式说明原因（如”这里不能放星”或”这里不需要排除”），不静默拒绝。
- 依据、观察和目标的差异不能只靠颜色；应同时依靠边界、层级或标记形态。
- INTRO 必须等待玩家手动确认，不能自动跳过；玩家确认后进入 SETUP、GUIDED 或 AUTONOMOUS。SUMMARY 表示课程完成状态，当前版本进入 SUMMARY 后立即写入完成记录并结束教学卡，没有 SUMMARY 手动确认按钮。
- 教学卡层级：INTRO 卡 > 教学步骤卡（SETUP/GUIDED/TRANSFER_PRACTICE）。SUMMARY 当前不保留可见教学卡；未来若改为可见总结页，必须另行设计和测试。
- 不增加复杂阶段进度条或步骤计数器；教学进度通过教学卡内容变化自然表达。
- E2E proof bridge 是测试接口，不属于玩家 UI；production build 中不得存在。

## 9. Motion 与反馈

Motion 的唯一来源是 `src/config/motionPresets.js`（JS）与 `src/index.css` 的 `--motion-*` 变量（CSS），两者语义一一对应。新 UI 改动必须复用这些 token 与公共预设，禁止在组件内新增任意毫秒字面量、easing 曲线或 spring 参数。

### Duration token

只使用五档，stagger 不是第六档：

| Token | 值 | 用途 |
| --- | --- | --- |
| Instant | 100ms | 格子按压等即时反馈 |
| Fast | 160ms | reduced-motion 下的 opacity 保留档、轻提示 |
| Base | 240ms | 常规面板、数值变化 |
| Emphasis | 420ms | 需要被注意到的状态进入 |
| Ritual | 800ms | 完成仪式类一次性动画 |

### Easing

只建立两种：Standard `cubic-bezier(0, 0, 0.2, 1)` 为默认；Emphasized `cubic-bezier(0.2, 0.75, 0.25, 1)` 用于需要强调的进入。

### Spring

只建立两组：Gentle（stiffness 300 / damping 22 / mass 0.6）用于普通一次性面板进入；Celebrate（stiffness 400 / damping 12 / mass 1）仅用于胜利星级、解锁徽标和重要奖励。高频格子、HUD、按钮、撤销和错误反馈禁止使用 spring。

### Stagger

固定步进 60ms，总 stagger 不超过 300ms；通过 `staggerDelay(index)` 计算，不写分散的延迟字面量。

### 状态语义

- 面板 / 背景：`winPanelEnter`、`backdropEnter`；Toast：`toastEnterExit`；解锁奖励：`unlockBadgeEnter`。
- HUD 数值变化：`hudValuePulse`；连击里程碑：`comboMilestonePulse`；生命扣除使用错误语义色的短 pulse。
- 教学卡切步：`teachingStepFade`（Base opacity crossfade，极轻微位移）。
- 棋盘：按压 `cellTap`、错误 `errorShake`；错误反馈用位移抖动而非常驻动画，且不依赖 spring。
- Star Line 撤销复用标记的现有 exit/enter 反馈，被撤掉的标记走 Fast exit overlay，不新增第二套撤销动画。
- 动画表达“发生了什么”的辅助语义，状态本身（错误文字、冲突边界、完成状态、数值）必须不依赖动画成立。

### Reduced-motion

- 全局入口：`main.jsx` 的 `MotionConfig reducedMotion="user"` 负责 Motion 组件；CSS 侧由 `index.css` 的全局 `prefers-reduced-motion` 基础与各区块规则负责；Tailwind `active:scale` 按压缩放在 reduced-motion 下以严格限定的 `!important` 关闭（components 层在构建产物中先于 utilities 层，不加 `!important` 会被 utility 覆盖）。三者各自受控，不能只依赖 MotionConfig。
- reduced-motion 下取消位移、缩放、shake、spring 弹跳和循环动画；页面进入使用独立的 opacity-only keyframe，面板与 Toast 使用 `fadeOnly`，均为 Fast 160ms 纯 opacity。
- 错误文字、冲突边界、完成状态和数值必须保留；声音不自动关闭。

### 声音原则

- 所有音效经 `soundEngine.js` 的 `safeTone` 合成，不加载音频文件、不引入音频依赖、不加背景音乐。
- 事件使用语义函数（放置星点、标 X、冲突、撤销、解锁、完成、失败、奖励），组件不直接写频率参数。
- 音效是反馈的增强层，不是状态的唯一表达；静音或 reduced-motion 下玩法信息必须完整。

### 禁止的装饰动画

- 无限循环的呼吸、漂浮、闪烁不得用于高频元素（格子、HUD、按钮）。
- 不以纯装饰动画拖延玩家操作节奏；仪式类动画一次性完成且可降级。
- 不得在组件内绕过公共 token 自行发明时长、曲线或 spring。

## 10. 令牌与改动流程

基础 CSS 语义令牌定义在 `src/index.css`：背景 / 表面 / 工作区 / 棋盘、主次文字、状态色、边界、圆角、间距、阴影与焦点光晕。玩法专属变量应建立在这些令牌之上，不能冒充全产品规则。

正式玩法的玩家可见规则说明以 [`docs/game-explanation-system.md`](./game-explanation-system.md) 和 `src/config/gameExplanations.js` 为准。UI 改动不得在组件内重新发明核心玩法用语。

后续每次 UI 改动都应：

1. 判断是否涉及本规范，并优先复用现有令牌。
2. 新增可复用规则时同步更新本文件。
3. 明确“本次落地页面”与“未来适用范围”。
4. 避免在模块内部堆积孤立的颜色、字号或状态逻辑。
5. 在最终汇报中说明调整了哪些产品级规则和哪些页面实际落地。
