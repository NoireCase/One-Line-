# One Line 玩法设计模板

本文档用于 One Line 后续新增玩法在开发前完成规格化。适用对象包括产品设计、AI 批量生成关卡、人工验收和 Codex 开发任务拆解。

使用原则：

- 先写清玩法规格，再进入代码开发。
- 只描述当前玩法需要的字段，不强行套用所有字段。
- 字段名必须与实际代码一致；如果代码尚未支持，必须标记为“待实现字段”。
- 每个新玩法都要说明是否影响 Classic、Diagonal、存档和评分。
- MVP 阶段优先验证玩法是否成立，不提前做大规模架构重构。

## 1. 玩法基本信息

每个新玩法立项时，先填写以下信息：

```md
玩法名称：
玩法类型：基础移动 / 特殊格 / 路径约束 / 评分变体 / 混合玩法
所属版本：
开发阶段：概念 / MVP / 测试关卡 / 正式关卡包
是否进入正式关卡包：是 / 否 / 待定
是否复用 Classic combo 评分：是 / 否
是否使用独立评分：是 / 否
是否需要独立结算面板：是 / 否
是否使用独立存档键：是 / 否
是否影响 Classic：是 / 否
是否影响 Diagonal：是 / 否
```

玩法类型示例：

- Classic：基础上下左右移动。
- Diagonal：允许八方向移动。
- Portal：特殊格触发目标出口。
- Obstacle：不可经过格或条件限制格。
- One-Way：只能按指定方向进入或离开。
- Bridge：允许跨越或连接原本不相邻区域。

## 2. 玩家可见规则

这里写玩家实际能看到、能理解、能操作的规则，不写内部实现细节。

必须说明：

- 玩家在棋盘上会看到什么特殊元素。
- 玩家如何操作这些元素。
- 什么情况下路径推进成功。
- 什么情况下操作无效或失败。
- 特殊格在未触发、触发、已访问时分别如何表现。
- 玩法是否改变“一笔画”的核心体验。

填写模板：

```md
玩家目标：
玩家看到的棋盘元素：
玩家操作方式：
成功条件：
失败或无效操作：
特殊格状态：
- 未触发：
- 触发中：
- 已访问：
是否需要额外教程：
```

示例判断：

- Portal 的玩家规则应描述为“进入入口后发现出口，必须手动连接到出口”，而不是“系统自动传送”。
- Obstacle 的玩家规则应明确哪些格不可经过，以及是否可通过道具或特殊条件解除。
- One-Way 的玩家规则应明确方向提示如何显示，避免玩家把它误认为普通箭头装饰。

## 3. 系统隐藏规则

这里写系统内部如何判断合法移动和状态变化。玩家不一定看到这些规则，但开发和验收必须明确。

必须说明：

- 合法移动如何判断。
- 路径是否必须覆盖全棋盘。
- 是否允许重复经过格子。
- 是否允许跨越、斜向、跳转或特殊连接。
- 特殊格何时触发。
- 特殊格触发后是否改变下一步目标。
- 失败条件如何判定。
- 是否影响道具、复活、保存退出、结算。

填写模板：

```md
移动规则：
路径覆盖规则：
重复经过规则：
特殊格触发条件：
触发后的系统状态：
下一步合法目标：
失败条件：
与道具系统关系：
与保存退出关系：
与结算关系：
```

设计要求：

- 新玩法不要隐式修改 Classic 或 Diagonal 的合法移动。
- 如果玩法需要独立规则，应有独立 mode config 或明确的规则分支。
- 如果玩法需要独立回访目标，必须先定义独立内容、结算目标和存档边界。

## 4. 关卡数据结构

关卡字段必须贴合实际代码。不要为了模板统一而强行给所有玩法添加同一批字段。

### 通用字段

以下字段适合多数玩法，但仍以实际代码为准：

```js
{
  id: 'level-id',
  name: '关卡名称',
  N: 5,
  path: [0, 1, 2],
  targetSteps: 24
}
```

字段说明：

- `id`：关卡唯一标识。
- `name`：关卡显示或维护用名称。
- `N`：棋盘尺寸，例如 `5` 表示 `5x5`。
- `path`：设计路径。数组内容通常是棋盘格索引。
- `targetSteps`：推荐最优通关步数。只有使用步数星级的玩法才需要。

### 扩展字段原则

不同玩法可以使用不同扩展字段：

```js
{
  portals: [
    { id: 'A', cells: [11, 24] }
  ],
  obstacles: [6, 12],
  oneWayTiles: [
    { cell: 8, direction: 'right' }
  ],
  bridgeTiles: [
    { from: 4, to: 20 }
  ],
  hiddenVals: [10, 14]
}
```

注意：

- 上方 `obstacles`、`oneWayTiles`、`bridgeTiles` 是未来玩法字段示例；只有代码支持后才能进入正式关卡数据。
- 当前 Portal 关卡真实字段是 `id`、`name`、`N`、`targetSteps`、`path`、`portals`、`hiddenVals`。
- 当前 Portal 运行时会生成 `portalId`，但 `portalId` 不是关卡源数据字段。
- 如果玩法需要 `specialTiles` 这种统一字段，必须先在代码里实现解析和渲染，再要求 AI 输出。

每个玩法规格必须写明：

```md
本玩法使用的字段：
必填字段：
可选字段：
禁止字段：
字段是否已被代码支持：
```

## 5. AI 生成关卡约束

AI 批量生成关卡时必须遵守：

- 关卡必须可通关。
- 设计路径必须可人工复核。
- 特殊机制必须有必要性。
- 不允许只是在普通关卡上随便放特殊格。
- 不允许纯靠猜测。
- 不允许视觉过度混乱。
- `targetSteps` 必须基于设计路径计算。
- 必须输出可人工复核的设计说明。
- 必须说明该关卡为什么属于当前玩法，而不是普通 Classic / Diagonal 关卡。

AI 输出每关时建议包含：

```md
关卡 id：
关卡名称：
难度：
使用机制：
设计路径摘要：
特殊格作用：
为什么必须使用特殊机制：
targetSteps 计算依据：
人工验收重点：
```

针对不同机制的约束示例：

- Portal：至少一个 Portal 必须改变路径规划，不只是装饰。
- Obstacle：障碍必须改变路线选择，不只是填充空位。
- One-Way：方向限制必须制造可理解的路径约束。
- Bridge：桥必须连接原本难以自然接续的区域。

## 6. 难度分级标准

难度不要只按棋盘大小判断，应综合以下维度：

- 棋盘尺寸。
- 路径长度。
- 特殊格数量。
- 误导路径数量。
- 是否需要跨区域规划。
- 是否需要记忆或推理。
- 是否容易误触。
- 是否需要玩家理解新状态。

### Easy

判断标准：

- 棋盘小或路径短。
- 特殊格数量少，通常 1 组或 1 类。
- 出口、方向、障碍等提示容易发现。
- 干扰路径少。
- 玩家能在一次尝试中理解核心规则。

适用目标：

- 教玩家新机制。
- 验证机制是否能被自然理解。
- 不追求高难误导。

### Normal

判断标准：

- 特殊格数量适中。
- 有轻微误导路线。
- 需要跨区域观察，但不需要长期记忆。
- 玩家可能需要 1-2 次尝试才能理解最优路径。

适用目标：

- 展示机制的主要变化。
- 开始要求玩家规划，而不是只跟随显性路径。

### Hard

判断标准：

- 特殊格数量较多，但仍保持可读。
- 需要跨区域规划。
- 有多个阶段的推理或路线接续。
- 错误路线存在，但可以通过规则推理排除。
- 不能依赖纯猜。

适用目标：

- 给熟悉机制的玩家提供挑战。
- 验证玩法是否支撑正式关卡包。

## 7. 评分与星级规则

每个玩法必须先决定评分归属：

```md
是否复用 Classic combo：
是否使用步数评分：
是否使用时间或生命加成：
是否需要独立结算面板：
是否写入独立 high score：
```

可选评分模型：

- Classic combo：适合强调连续画线表现的玩法。
- 步数评分：适合 Portal、Obstacle、Bridge 等强调规划路径的玩法。
- 完成状态评分：适合早期 MVP，只验证能否通关。

星级规则必须明确：

```md
3 星：
2 星：
1 星：
失败：
```

设计要求：

- 不要让新玩法默认复用 Classic combo，除非玩法确实强调连击。
- 如果使用步数评分，`targetSteps` 必须来自设计路径。
- 如果结算面板显示内容不同，应先定义 UI 再开发。

## 8. UI 表现规范

UI 的目标是让主路径最清楚，特殊机制第二清楚。

必须说明：

- 特殊格如何显示。
- 未触发状态如何显示。
- 触发中状态如何显示。
- 已访问状态如何显示。
- 当前选中或当前路径头如何显示。
- 错误或无效操作如何反馈。

通用原则：

- 主路径视觉优先级高于特殊格提示。
- 已访问格应优先显示路径数字或路径状态。
- 特殊格未触发时可以弱化显示，避免提前暴露解法。
- 触发状态可以高亮，但不要压过主路径。
- 避免永久连线。
- 避免过度发光。
- 避免文字拥挤。
- 避免同一格同时显示过多信息。

玩法示例：

- Portal：未访问显示 `?`，激活出口高亮，已访问显示路径数字。
- Obstacle：不可走格应清楚但不抢主路径视觉。
- One-Way：方向箭头必须可读，已访问后仍要能看清路径顺序。
- Bridge：桥连接关系应在需要时提示，避免全局永久连线造成混乱。

## 9. 人工验收清单

每个新玩法和每批关卡都应人工验收：

- 是否可通关。
- 是否能稳定复现。
- 是否有玩法必要性。
- 是否规则容易解释。
- 是否与现有模式冲突。
- 是否影响存档。
- 是否影响 Classic。
- 是否影响 Diagonal。
- 是否影响道具、复活、保存退出。
- 是否适合进入正式关卡包。
- 特殊格是否清晰。
- 主路径是否清晰。
- `targetSteps` 或评分是否合理。
- AI 生成说明是否能被人工复核。

验收结论建议使用：

```md
验收结果：通过 / 需调整 / 不进入正式包
主要问题：
是否需要改规则：
是否需要改 UI：
是否需要改关卡：
是否需要改评分：
```

## 10. 上线前决策

玩法从 MVP 到正式上线前，需要回答：

- 这个玩法是否比 Classic 提供了新的思考方式？
- 玩家是否能在 1-2 关内理解规则？
- 这个玩法是否值得做 10 关？
- 是否值得进入 v1.0？
- 是否需要独立评分？
- 是否需要独立教程？
- 是否适合 AI 批量生成？
- 是否需要独立存档键？
- 是否会增加维护成本？
- 是否会让主路径读图变差？

上线前建议分三档决策：

- 保留 MVP：玩法成立，但暂不进入正式包。
- 进入正式包：规则清晰，关卡可扩展，UI 可读。
- 暂停：玩法有趣但不稳定，或与 One Line 核心体验冲突。
