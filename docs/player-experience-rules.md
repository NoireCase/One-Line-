# One Line 玩家体验硬约束

本文档是 One Line 后续 UI、评分、模式、关卡和结算设计必须遵守的玩家体验约束。

它不是功能清单，也不是普通 PRD。任何新增或修改都应先检查是否符合本文档。

正式玩法的玩家说明、术语与落点另见 [`docs/game-explanation-system.md`](./game-explanation-system.md)。页面不得自行改写核心规则；需要改写时，应先同步该规范和统一文案源。

## 1. 产品定位

One Line 是一款轻度路径规划 Puzzle。

它不是纯硬核逻辑推理游戏，也不是街机动作游戏。

核心体验是：

```text
观察棋盘
↓
思考路径
↓
规划路线
↓
执行一笔画
↓
获得反馈
↓
完成关卡
```

执行过程中的 Combo、分数、动画和音效也是体验的一部分，不应被全部删除。它们负责提升连线时的节奏和爽感，但不能压过路径规划本身。

## 2. 核心玩家目标

玩家的主目标是：

- 继续推关。
- 完成更多关卡。
- 看到进度增长。
- 获得通关奖励。

满星不是所有玩家的默认目标。

三星是单关挑战目标，不是主线推进压力。玩家即使没有满星，也应能够自然继续后续关卡。

## 3. 页面职责

### Home

首页只负责让玩家快速继续或开始游戏。

不要在首页堆叠模式规则、成长说明或复杂入口。

### Mode Select

模式选择页主要展示：

- 可选择的模式。
- 每个模式的完成度。

不要堆叠复杂规则、内部分类或长篇说明。

### Level Select

关卡选择页主要让玩家知道：

- 自己玩到哪里。
- 下一关在哪里。
- 后面还有多少内容。
- 哪些关卡已经完成。

### Game

游戏页只服务专注解题。

不要持续提醒玩家当前能拿几星，也不要出现“已失去三星”“当前可得★★”等监控感提示。

### WinPanel

结算页不是判卷页，而是奖励页。

它应通过星级、分数逐项跳出、金币和按钮节奏，让玩家感受到通关后的成就感。

## 4. Level Select 约束

- 第一视觉焦点应是当前可挑战关卡。
- 已完成关卡可以展示星级，作为玩家的足迹和荣誉。
- 未解锁关卡应保持灰态或锁定状态，表达后续内容仍然存在。
- 不要在显著位置展示“总星数 xx/xx”等全局星级进度条。
- 不要让玩家为了选关而计算星级、分数或解锁条件。
- 不要让星级变成主线 KPI。

星级只属于单关表现，不应成为主线推关压力。

## 5. Game 页面约束

游戏页面应保持克制，让棋盘和路线成为视觉中心。

可以显示：

- 当前关卡。
- 生命。
- 分数。
- 时间。

不推荐显示：

- 当前可得几星。
- 三星是否已经失去。
- 距离三星还差多少。
- 强提示式评分条件。
- 持续变化的评价说明。

玩家在游戏中应专注观察棋盘和完成连线，而不是被评分信息打扰。

## 6. WinPanel 约束

结算页应采用奖励式节奏。

推荐结构：

```text
CLEAR / 通关完成

时间：MM:SS:CC

星级区域置顶

分数项目逐项跳出

随着分数增长，星星逐颗点亮

显示总分

显示金币奖励

下一关 / 回到首页
```

结算页不要优先解释“为什么不是三星”。

如果需要说明，应作为弱信息或可展开详情，不能盖过通关奖励和继续游戏的行动入口。

## 7. 时间系统约束

- 时间不作为失败条件。
- 不使用倒计时制造硬压力。
- 时间用于记录感和轻度压力。
- 结算页时间格式统一为 `MM:SS:CC`。
- `CC` 表示两位百分秒，用于保持显示规整。

时间不能成为主线推进门槛。

## 8. Combo 与分数约束

Combo、分数、动画和音效应保留。

它们用于提升执行一笔画时的节奏、反馈和爽感。

同时必须遵守：

- 不要让 Combo 绑架主线推关目标。
- 不要让分数成为正常解锁关卡的门槛。
- 不要让玩家觉得必须反复刷分才能继续游戏。
- 分数可以提供表现反馈和奖励，但不能压过通关本身。

## 9. Portal 约束

Portal 当前的定位是：

> 带空间跳转的路径规划玩法。

当前不要提前将 Portal 定义为“步数策略模式”。

在全局产品规则尚未完全稳定前，不为 Portal 单独建立复杂评分体系。

Portal 应先符合全局体验：

- 清晰。
- 好理解。
- 反馈明确。
- 不打断推关节奏。

如果后续关卡确实具备明显的路线选择、传送顺序规划和路线优化价值，再单独讨论步数制或专项评价。

## 10. Hidden 与新机制约束

Hidden 后续可以作为毕业挑战，但不应过早设计成高压硬核模式。

Hidden 应优先复用现有机制，作为完成普通内容后的长期目标。

Bridge、Obstacle、One-Way 等新机制暂缓。

在以下内容稳定前，不新增横向机制：

- 当前产品体验。
- 页面信息层级。
- 生命和星级反馈。
- 通关结算。
- 普通关卡到 Hidden 的推进过程。

## 11. 总体红线

任何后续设计都应避免：

- 让玩家感觉自己在参加考试。
- 让玩家在选关页进行数学计算。
- 让星级变成主线 KPI。
- 让 Game 页面出现过多系统监控信息。
- 让结算页变成判卷说明。
- 为了机制丰富而增加玩家理解成本。
- 用复杂说明代替清晰反馈。
- 用外围成长系统掩盖核心推关体验的问题。

## 12. Star Line 术语与前台表达

Star Line 的玩家可见术语必须避免混淆。

推荐用法：

- `星点`：玩家在棋盘上放置的对象。
- `单星规则`：每一行、每一列、每片星域都需要 1 个星点。
- `双星规则`：每一行、每一列、每片星域都需要 2 个星点。
- `N×N`：关卡棋盘尺寸。

不推荐在 Star Line 正式 UI 中使用：

- `通关三星` 作为主要评价目标。
- `starRating` 作为玩家可见文案。
- `配额` 这类偏系统字段的词。
- 把单星 / 双星规则写成关卡评分星级。

Star Line 的完成反馈应强调规则成立、星线点亮、区域关系被正确解开，而不是让玩家感觉被星级评分系统判卷。

## 后续开发检查清单

Codex 或其他 AI 修改功能前必须逐项自查：

- [ ] 新增 UI 是否增加了玩家认知负担？
- [ ] 是否把满星当成了默认主目标？
- [ ] 是否打断了 Game 页面的专注感？
- [ ] 是否让 Level Select 变成星级 KPI 页面？
- [ ] 是否让 WinPanel 失去了奖励感？
- [ ] 是否引入了尚未验证的新机制？
- [ ] 是否符合轻度路径规划 Puzzle 的定位？

如果任意一项存在明显风险，应先缩小方案或停止实现。
