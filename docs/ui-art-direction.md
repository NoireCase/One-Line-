# One-Line UI Art Direction

## 1. 文档目的

本文档用于约束后续 AI / Claude / Codex 修改 One-Line UI 时的审美方向。

它不是普通 UI 规范，也不是完整设计系统。它不替代 `CLAUDE.md` 的工程规则，也不替代 `docs/player-experience-rules.md` 的玩家体验约束。

它只回答一个问题：

```text
什么样的 UI 看起来像 One-Line，什么样的 UI 不像。
```

后续涉及玩家界面的 UI 修改，应优先参考本文档，再决定是否动手。

## 2. 产品气质

One-Line 是一款夜色里的轻量路径解谜游戏。

它的核心气质是：

- 安静，但不是冷冰冰。
- 克制，但不是空白。
- 有手绘路径感，但不是儿童涂鸦。
- 有通关奖励感，但不是街机爆炸特效。
- 有一点神秘感，但不能让玩家看不清棋盘。

当前项目已经形成的视觉基础包括：

- 深色夜景背景。
- 手绘感路径、节点和虚线装饰。
- 柔和边框和轻微纸面/棋盘质感。
- 金色主按钮作为明确行动入口。
- 棋盘格、路径线、当前格、目标格作为游戏主视觉。

One-Line 不是 SaaS 工具，不是后台面板，不是营销落地页，也不是重特效手游界面。

## 3. UI 总原则

### 棋盘第一

游戏页中，棋盘必须永远是第一视觉焦点。

HUD、道具、Toast、提示、评分、进度和按钮都只能服务棋盘，不能抢走注意力。

可接受：

- 棋盘居中。
- 路径线清楚。
- 当前格明显。
- 已走格、目标格、隐藏格、传送门、金币能被快速辨认。

不可接受：

- HUD 比棋盘更亮。
- 大段说明压在棋盘上方或下方。
- 弹窗频繁打断解题。
- 为了装饰加入和路径无关的大面积图形。

### 模式差异第二

五种玩法必须有各自的记忆点。

模式差异不能只靠换颜色。每个模式至少需要在以下维度里有两个明显差异：

- 小插画形态。
- 规则关键词。
- 关卡卡片状态表达。
- 规则卡或入口说明。
- 棋盘符号。
- 结算文案和数据重点。

### 说明文字第三

One-Line 的玩法应通过棋盘、符号和反馈让玩家理解。

文字只负责点醒，不负责讲课。

每个入口说明优先使用一句短句。需要更多解释时，放在规则卡、可展开详情或首次进入提示里。

## 4. 页面优先级

### Home

首页只负责两件事：

1. 继续游戏。
2. 进入玩法选择。

首页应保持安静、有游戏感。不要加入模式表格、版本历史、功能列表或开发说明。

主按钮必须明确。设置、积分等信息只能弱化显示。

### Mode Select / Mode Detail

当前模式选择和模式详情主要由 `PuzzleBookPage` 与 `ModeSwitcher` 承担。

这里的优先级是：

1. 当前选中的玩法是什么。
2. 当前完成度是多少。
3. 这个玩法和其他玩法有什么不同。
4. 下一步应该点哪里。

模式详情不需要长篇规则说明，但需要给每种玩法一个清楚的玩家记忆点。

### PuzzleBook / Level Select

关卡选择页的第一视觉焦点应是当前可挑战关卡。

状态优先级：

1. 当前可玩 / 推荐下一关。
2. 已完成。
3. 有存档。
4. 未解锁。
5. 历史分数或星级。

60 关长列表不能只变成一面锁定卡片墙。后续整理时，应优先考虑分段、当前关定位、继续挑战入口，而不是堆更多说明。

### GameView

游戏页应让玩家自然进入：

```text
看棋盘 -> 找下一步 -> 连线 -> 获得反馈
```

HUD 只显示当局必要信息。分数、时间、生命、步数可以存在，但不要变成监控面板。

### WinPanel

胜利面板是奖励页，不是判卷页。

优先级：

1. 通关完成的情绪反馈。
2. 下一关按钮。
3. 模式相关成绩。
4. 可展开详情。
5. 返回或重玩。

星级、分数、金币、步数都应服务成就感，不能让玩家觉得自己被系统批改。

### LosePanel

失败面板应清楚告诉玩家下一步怎么做。

它可以简短，但不能含糊。尤其是 Portal Collect、Hidden 等特殊玩法，失败反馈应尽量贴近具体原因。

## 5. 五种玩法的视觉记忆点

### Classic

定位：基础旅程。

视觉方向：

- 最标准、最安静的 One-Line 体验。
- 以顺序数字、连续路径、当前格为中心。
- 色彩应稳定、亲和、低压力。

避免：

- 做成新手教程页。
- 过度强调分数或满星。
- 和 Diagonal 使用完全相同的路径图形。

### Diagonal

定位：斜向规则。

视觉方向：

- 需要让玩家一眼感到“路径方向变多了”。
- 小插画和规则卡应突出斜线、折线、八向连接。
- 游戏内不需要持续解释斜向规则，但入口和首次解锁必须明确。

避免：

- 只把 Classic 换成蓝色。
- 让斜向规则藏在长文字里。

### Hidden

定位：极简线索 / 推理挑战。

视觉方向：

- 稀疏数字是核心记忆点。
- 空格、关键数字、分段推理感要比奖励系统更突出。
- 结算应强调“用关键数字还原路径”，而不是星级刷分。

避免：

- 在 Hidden 中继续强化金币、道具、星级等普通模式暗示。
- 把 Hidden 做成高压考试感。
- 用大段说明替代棋盘上的线索感。

### Portal Classic

定位：传送门路径。

视觉方向：

- 重点是空间跳转和路径不断开。
- 传送门入口、出口、激活态要清楚。
- 入口插画和规则卡应强调“进入门 -> 出口亮起 -> 继续路径”。

避免：

- 使用“旧传送门”等开发历史口径作为玩家文案。
- 让 Portal 看起来只是紫色版 Diagonal。

### Portal Collect

定位：金币目标 / Collect and Exit。

视觉方向：

- 重点是金币、终点、传送门、步数目标。
- 起点、终点、金币、传送门、障碍必须有清晰层级。
- 入口和规则卡应表达“吃完金币，再去终点”。

避免：

- 使用 Classic 的道具栏气质。
- 让金币目标被传送门说明淹没。
- 让规则卡继续使用通用绿色，而没有收集目标的金色记忆点。

## 6. 文案原则

玩家文案要像游戏，不要像开发记录。

推荐风格：

- 短句。
- 动词明确。
- 直接描述玩家要做什么。
- 有一点氛围，但不影响理解。

可接受示例：

```text
顺着数字，把整张棋盘连成一条路。
只给关键数字，推完整路线。
吃完所有金币，通过传送门抵达终点。
路线中断了，再试一次。
```

禁止风格：

```text
旧传送门
prototype
demo
v2 样板
当前处于早期验证阶段
该模块用于测试候选关卡
```

开发历史、内部版本、GM 术语、脚本流程不应出现在玩家界面。

说明文字不能堆叠。若一个页面需要三段以上说明，优先重新设计信息层级，而不是继续加字。

## 7. 禁止事项

后续 UI 修改明确禁止以下方向：

- 大面积工具面板感。
- 把游戏页做成数据仪表盘。
- 所有模式只是换颜色。
- 过度玻璃拟态。
- 过度发光、过度渐变、过度阴影。
- 大面积紫蓝渐变背景。
- 说明文堆叠。
- 主次不分的卡片堆叠。
- 页面里卡片套卡片。
- 用营销页 hero 替代可玩的游戏界面。
- 在玩家文案中出现开发历史口径。
- 在 GameView 中持续展示“失去三星”“还差几步满星”等压力信息。
- 为了视觉差异新增外部素材或依赖。
- 为了统一样式而削弱玩法符号的辨识度。

## 8. 移动端原则

移动端优先保证可玩，不优先保证信息完整。

要求：

- 棋盘必须完整可见，且点击区域足够大。
- 主按钮不能被底部安全区、浏览器栏或弹窗遮挡。
- HUD 可以压缩，但不能压到难以识别。
- 模式切换如果横向滚动，必须让玩家知道还有更多模式。
- 60 关列表在手机上不能让当前关丢失在信息噪音里。
- 弹窗高度必须可控，不能让主要按钮掉出首屏。

移动端不应为了显示所有信息而牺牲棋盘尺寸。

## 9. AI 修改 UI 的工作方式

AI 修改 One-Line UI 时，应按这个顺序工作：

1. 先确认本次修改属于哪个页面和哪种玩法。
2. 先保护棋盘、路径、关卡状态和结算主按钮。
3. 只在必要文件内小范围修改。
4. 不引入新依赖。
5. 不改变玩法规则、关卡数据、存档 key 或评分逻辑，除非任务明确要求。
6. 修改模式视觉时，同时检查入口、关卡卡片、游戏符号和结算是否一致。
7. 修改文案时，删除开发口径，保留玩家能理解的短句。
8. 修改后至少检查桌面和移动端首屏。

常见错误：

- 只改颜色，没有改玩法记忆点。
- 为了说明清楚而写太多字。
- 把 Settings、GM、关卡工具的风格带到玩家主界面。
- 让 WinPanel 变成成绩审计表。
- 让 LosePanel 只剩一句泛泛失败提示。
- 让 PuzzleBook 变成 60 个同质方块的列表。
- 在 Hidden 中继续展示普通模式的奖励暗示。
- 在 Portal Collect 中没有突出金币和终点目标。

## 10. UI 修改验收清单

每次 UI 修改后，至少检查以下问题：

- [ ] 棋盘是否仍是 GameView 的第一视觉焦点？
- [ ] 玩家第一眼是否知道该点哪里？
- [ ] 主按钮是否比次要按钮更突出？
- [ ] 五种玩法是否不只是换颜色？
- [ ] 当前可挑战关卡是否清楚？
- [ ] 已完成、未解锁、有存档状态是否容易区分？
- [ ] Hidden 是否避免了不必要的金币、道具、星级暗示？
- [ ] Portal Classic 是否突出传送门路径？
- [ ] Portal Collect 是否突出金币、终点和步数目标？
- [ ] WinPanel 是否像奖励页，而不是判卷页？
- [ ] LosePanel 是否告诉玩家下一步怎么做？
- [ ] 文案是否没有 demo、prototype、旧版本、GM 等开发口径？
- [ ] 移动端是否没有文字溢出、按钮遮挡或弹窗过高？
- [ ] 是否没有新增外部素材或依赖？
- [ ] 是否没有改变玩法逻辑、关卡数据、存档结构或评分规则？

如果任一项不满足，应优先缩小修改范围，先修正体验风险，再继续做视觉增强。
